# 特性开关双轨切换实现模式

目标:同一个业务请求,能在"调用旧存储过程"和"调用新 Java 实现"之间按配置切换,切换的判断依据同一个业务主键必须稳定(同一个 orderId/userId 等每次路由结果一致),不依赖随机数——这样生产灰度出问题时能直接定位到"是哪一批业务对象在走新代码",且能稳定复现,不会变成偶发难查的线上问题。

## 组成部分

**1. 开关配置**:一个 `@ConfigurationProperties` 类,至少两个字段:`enabled`(总开关)+ `rolloutPercentage`(灰度百分比,0-100)。改值需要重启应用生效,不做运行时热更新——这是故意的摩擦力:换取"配置被误改导致流量突然全切换"的风险降低,不是技术能力做不到。

**2. 旧存储过程网关**:生产代码里调用真实存储过程的入口,用 `DataSourceUtils.getConnection/releaseConnection` 获取连接 + 原生 `CallableStatement` 调用,不要依赖任何测试专用的工具类(测试目录下的类不能被 main 代码引用)。

**3. 路由服务**:接收业务主键,按 `Math.floorMod(businessKey.hashCode(), 100) < rolloutPercentage` 决定调路由到 Java 实现还是网关。总开关关闭时,不管百分比,一律走网关。

**4. 统一异常映射**:不管走哪条路径抛出的业务异常(Java 侧的 checked/unchecked 异常,还是网关捕获到的 SQLSTATE),对上层调用者(Controller/其他 Service)呈现同一种异常契约,避免调用方需要区分"这次走的是新是旧"。

## 验证方式

- 开关关闭:请求应该只命中网关调用路径
- 开关开启+灰度100%:请求应该只命中 Java 实现路径
- 开关开启+灰度部分百分比:同一个业务主键反复请求,路由结果应该稳定不变;不同业务主键之间的路由分布应该大致符合配置的百分比
- 异常场景(存储过程和 Java 实现都应该失败的输入):两条路径返回的异常类型/错误码应该一致
