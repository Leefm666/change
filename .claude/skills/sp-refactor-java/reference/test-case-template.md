# 测试用例设计表格

Step 4 产出的场景清单,先于任何测试代码存在,自然语言描述,不写代码。之后阶段一的两个 IT(存储过程行为验证 + Java对比存储过程)、阶段二的开关双路径断言,都共用这份场景清单里的场景名字,保证同一个输入在各层验证里指向同一件事。

## 场景清单

| 场景名 | 输入 | 覆盖的分支/边界/全局变量ID(引用详设文档编号) | 预期结果(成功值/异常类型+SQLSTATE) | 预期的表状态变化 |
|---|---|---|---|---|
| | | | | |

## 覆盖矩阵(必填,不能用"均已覆盖"代替)

行是详设文档里的每一个 ID,列是命中它的场景名。一个 ID 至少命中一个场景;一个 ID 长期在这张表里找不到任何命中场景,说明用例清单还没设计完,不能进入 Step 5。

| ID | 类型 | 命中的场景名 |
|---|---|---|
| B1 | 分支 | |
| E1 | 边界条件 | |
| G1 | 全局变量 | |

## 覆盖要求(逐条自检,不能跳过任何一条)

- 详设文档"分支清单"里的每一个分支ID,在覆盖矩阵里至少命中一个场景。
- 详设文档"边界条件矩阵"里标记为"适用"的每一个边界ID,至少命中一个场景;标记"不适用"的不需要场景,但要能在详设文档里找到不适用的理由。
- 涉及包全局变量的 procedure/function,E5(多次调用间读写时序)必须有场景验证:同一连接内连续调用两次、用不同的业务对象/上下文,断言互不串号。
- 多因素交叉场景:至少设计一个"两个以上失败条件同时满足"的场景(例如权限超限同时命中扣款异常),验证数据库真实的判断顺序(先报哪个错),不要假设"先写的分支先判断"就是真实顺序——这类顺序必须实测,不能凭代码顺序猜。
- 数值边界:涉及分级判断(累进税率、阈值分档)的字段,至少设计"恰好等于边界值"和"边界值±1"两个场景,验证闭区间/开区间语义,不能只测"落在某档中间"的安全值。
