# 包全局变量 → Java 映射判断树

openGauss package 里声明在包头或包体顶层的全局变量,在同一数据库会话(session)内跨多次 procedure/function 调用保持状态。Java 方法调用没有这种隐式会话状态,必须显式判断每个全局变量该映射成什么,不能想当然地用一个 static 字段照抄"全局"这个表面语义了事——那样会把"数据库会话级状态"错误地映射成"JVM 进程级状态",在多用户并发场景下产生跨会话数据污染。

对每个全局变量,按顺序判断:

## 1. 是否真的跨调用持续?
先确认这个变量不是"包内多个函数共享一个名字,但每次调用前都会被重新赋值,从不依赖上次调用遗留的值"这种情况。如果每次使用前都先写后读,它本质是一个可以用局部变量/方法参数替代的临时中间量。

→ 是纯临时中间量:直接消化成 Java 方法内的局部变量或参数,不需要额外设计,记录结论"纯临时中间量,直接内联"。

## 2. 是否只是同一次业务调用链内、包内多个 procedure/function 之间传递的中间状态?
比如包头某个 public 方法调用了包内多个 private 方法,这些 private 方法通过全局变量互传数据,但这条调用链结束后这个变量的值不会被下一次外部调用依赖。

→ 是:映射成 Java 方法参数或返回值显式传递,不引入任何跨方法调用的隐藏状态,记录结论"显式参数传递"。

## 3. 是否真的需要跨越多次外部调用保持状态(比如统计计数器、上次处理的游标位置)?
→ 是:这是真正的会话级/业务级状态,不能用 JVM static 字段代替(并发/多实例场景下会出错)。需要判断这个状态的持久化载体应该是什么——数据库表字段、Redis、还是别的机制,这个决定涉及生产环境的并发模型和一致性要求,**不由 skill 自行决定**,记录结论"需业务方确认状态载体",列进详设文档的"待确认项"。

## 4. 变量本身是不是历史遗留的死代码(写了但从没被真正读取过,或者读取结果不影响任何可观测输出)?
直连数据库验证阶段(Step 6)如果观察到某个全局变量无论取值如何都不影响存储过程的输出,记录这个发现,同样放进"待确认项"——是否可以在 Java 实现里安全省略这个变量,需要业务方确认这不是一个未来会被激活的开关,而不是开发自行判定"看起来没用就删掉"。
